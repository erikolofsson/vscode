# Chat — Accessibility (screen readers, ARIA, voice)

This document summarizes the accessibility surface of the Chat subsystem (screen-reader text, ARIA roles, voice synthesis signals, and accessible view hints) and lists porting considerations for bringing the same accessibility behavior to another platform.

## Responsibilities
- Provide concise, informative ARIA labels for chat items (requests and responses) so screen readers can announce meaningful content.
- Send accessibility signals and voice synthesis triggers for request/response lifecycle events.
- Produce accessible alerts for elicitation dialogs and tool-confirmation flows.
- Expose a concise "accessible view" hint that can be opened by assistive tooling.

## High-level behavior (what the code does)
- Accessibility signals:
  - When a user sends a request, ChatAccessibilityService.acceptRequest() increments an internal request id and plays an accessibility signal: AccessibilitySignal.chatRequestSent.
    - It also registers a short-lived AccessibilityProgressSignalScheduler (configured by CHAT_RESPONSE_PENDING_ALLOWANCE_MS) to indicate an in-progress response.
    - See [`src/vs/workbench/contrib/chat/browser/chatAccessibilityService.ts:1`](src/vs/workbench/contrib/chat/browser/chatAccessibilityService.ts:1).
  - When a response arrives (acceptResponse), the service cancels the pending scheduler, plays AccessibilitySignal.chatResponseReceived, and posts a status message (rendered plain-text) for screen readers. If an elicitation is triggered, it sends a separate signal (chatUserActionRequired) and triggers alert().
- Accessible labels for list elements:
  - ChatAccessibilityProvider implements IListAccessibilityProvider and computes labels for both requests and responses.
  - For responses it composes a compact spoken label that may include:
    - Tool invocation confirmation hint (generated by getToolConfirmationAlert, which uses keybinding labels),
    - Counts of tables, file-trees, code blocks,
    - Any elicitation title/message,
    - The rendered plain text of the response (via the Markdown renderer/lexer).
  - The provider consults the IAccessibleViewService to include a short "open accessible view" hint based on user verbosity preferences.
  - See [`src/vs/workbench/contrib/chat/browser/chatAccessibilityProvider.ts:1`](src/vs/workbench/contrib/chat/browser/chatAccessibilityProvider.ts:1).

## Key implementation details to preserve when porting
- Use explicit accessibility signals (or platform equivalent) for these lifecycle events:
  - chatRequestSent (user-initiated),
  - chatResponseReceived (response ready),
  - chatUserActionRequired (elicitation / confirmation).
- When announcing response content:
  - Prefer a single, concise status/alert string derived from the Markdown content rendered to plaintext (use the same/in-line Markdown -> plaintext logic).
  - Include contextual hints like "1 table" / "3 tables", "1 code block" or the presence of tool invocations and whether they require explicit confirmation.
- Respect user accessibility settings:
  - Honor an "auto-synthesize" / voice-synthesis config flag before speaking responses (the code checks AccessibilityVoiceSettingId.AutoSynthesize).
  - Honor accessible view verbosity level (AccessibilityVerbositySettingId.Chat) — only include the extra "open accessible view" hint when requested.
- For tool invocations requiring confirmation:
  - The provider builds a short hint that references keybinding labels for accept/cancel actions (via IKeybindingService.lookupKeybinding(...).getAriaLabel()) so users know how to act without visual context.
  - See the helper used to format tool confirmation hint in [`src/vs/workbench/contrib/chat/browser/chatAccessibilityProvider.ts:1`](src/vs/workbench/contrib/chat/browser/chatAccessibilityProvider.ts:1).

## UX flows and screen-reader scenarios
- Send request:
  - acceptRequest() plays a "request sent" signal and schedules progress notification. Screen-reader focus workflows should be able to announce "Sending request" and then later "Response received".
- Response streaming / progressive rendering:
  - The service intentionally schedules and cancels progress signals so brief server latencies do not produce noisy repeated announcements. Preserve the short allowance timer (CHAT_RESPONSE_PENDING_ALLOWANCE_MS ≈ 4000ms) behavior to avoid announcing partial/too-frequent updates.
- Elicitation (user action required):
  - Calls alert(title + message) to create an immediate, high-priority announcement and plays the chatUserActionRequired signal.
- Tool confirmation:
  - If a response contains a tool invocation that requires confirmation, the provider appends a short hint that includes keybinding hints for accept/cancel.
  - This avoids forcing users to visually inspect the UI; they can act via keyboard.

## Porting checklist (minimal)
- [ ] Provide an AccessibilitySignal-like registry that the chat code can call (or map to platform-provided equivalents).
- [ ] Implement a short-lived progress-signal scheduler (allowManyInParallel semantics) to avoid noisy announcements for short-running responses.
- [ ] Provide a service to render Markdown -> plaintext for announcements (preserve the same sanitization and trimming semantics).
- [ ] Provide a way to query resolved keybinding labels for commands so confirmation hints are meaningful.
- [ ] Implement an AccessibleView/verbosity setting and a way to provide an "open accessible view" hint.
- [ ] Ensure "alert" and "status" primitives exist (aria live regions or platform speech APIs) to surface messages immediately.
- [ ] Add automated tests that assert:
  - acceptRequest triggers request-sent signal and creates pending scheduler,
  - acceptResponse cancels scheduler and posts status text,
  - elicitation triggers alert and the user-action-required signal,
  - ARIA labels generated by ChatAccessibilityProvider for a complex response (tables/codeblocks/tool invocations) contain expected phrases.

## Testing notes
- Unit tests:
  - Mock IAccessibilitySignalService and assert signals played with expected parameters.
  - Mock IKeybindingService to ensure tool-confirmation hint string contains keybinding labels.
- Integration tests:
  - Simulate a streaming response and assert only a single "response received" status is produced after completion; verify no excessive interim announcements.
  - Verify elicitation alerts are surfaced immediately and that synthesized-voice behavior respects AccessibilityVoiceSettingId.AutoSynthesize.
- Accessibility QA:
  - Use TalkBack / VoiceOver to manually confirm that:
    - the concise labels are announced for requests and responses,
    - the "open accessible view" hint appears only when verbosity setting requests it,
    - tool-confirmation hints include actionable keybindings.

## Risks and notes
- Race conditions: progressive streaming may interact with status updates; keep the short pending allowance to avoid announcing partial responses.
- Dependence on global keybinding lookup: when porting, ensure the keybinding lookup returns localized, human-readable labels.
- Voice synthesis toggles: do not auto-speak when a user-config indicates "do not auto-synthesize"; instead surface via status live-region only.
